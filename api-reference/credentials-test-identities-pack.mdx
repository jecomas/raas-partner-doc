## Partner API — Credentials & test identities pack (QA)

**Audience:** QA, partner onboarding, platform operations, and security.  
**Goal:** Define exactly which credentials and test identities QA needs, where they live, how they are rotated, and how they are requested.

**Scope:** Partner API tested online (black-box). This document does not publish secrets; it defines the operational package and governance.

## 1. Purpose and usage

This pack ensures QA can execute tests end-to-end without waiting on ad hoc credential requests.  
It covers:

- `api_key` provisioning by scope profile.
- Tenant and identity fixtures per environment.
- Access and rotation policies.
- Escalation for expired, revoked, or missing credentials.

## 2. Required package per environment

For each environment in the environment matrix, provide at minimum:

| Item | Required | Notes |
|------|----------|-------|
| Base URL | Yes | Include mTLS base URL if enabled. |
| OpenAPI link | Yes | Must match deployed version under test. |
| QA tenant IDs/codes | Yes | At least one tenant per core test flow. |
| `api_key` for `partner` | Yes | Used for request-funds/user flows. |
| `api_key` for `partner_send` | Yes | Used for send-funds flows. |
| `api_key` for `partner_full` | Yes | Used for full/express flows. |
| mTLS certificate pair | Conditional | Required only for tenants/environments with mTLS enabled. |
| Webhook callback secret/signature key | Conditional | Required if webhook signature validation is enforced. |
| Expiration date per credential | Yes | Include rotation owner and rollover date. |

## 3. Standard credential profiles

Define named profiles so QA can reference them consistently in test cases and bug reports.

| Profile ID | Scope set | Intended usage | Environment(s) | Owner | Rotation |
|------------|-----------|----------------|----------------|-------|----------|
| `qa-partner-basic` | `partner` | User registration, contacts, request money | `<env-list>` | `<owner>` | `<policy>` |
| `qa-partner-send` | `partner_send` | Send flow, source debit operations | `<env-list>` | `<owner>` | `<policy>` |
| `qa-partner-full` | `partner_full` | Full/atomic endpoints and certified flows | `<env-list>` | `<owner>` | `<policy>` |
| `qa-partner-mtls` | `partner` / `partner_send` / `partner_full` + mTLS | mTLS-specific validation | `<env-list>` | `<owner>` | `<policy>` |

> Keep profile IDs stable across releases. Replace values, not IDs.

## 4. Test identities model

QA needs predictable identities for repeatable results. Provide fixtures for:

| Identity type | Minimum set | Required fields | Example naming |
|---------------|-------------|-----------------|----------------|
| Requester user | 2-3 per tenant | Country, phone/email, KYC level, status | `qa_<env>_<tenant>_req_01` |
| Receiver/contact | 2-3 per tenant | Country, payout corridor, contact status | `qa_<env>_<tenant>_rcv_01` |
| Funding source | 2-3 tokens | Type (card/bank), active/inactive state | `qa_<env>_<tenant>_src_01` |
| Negative identity | 1-2 | Blocked/invalid/edge constraints | `qa_<env>_<tenant>_neg_01` |

Do not use real customer data. All fixtures must be synthetic or irreversibly masked.

## 5. Identity state catalog (must be explicit)

For each identity fixture, document:

- Current KYC/CIP state.
- Enabled corridors.
- Allowed operation types (request/send/full).
- Expected limits (min/max).
- If reusable or one-time only.

Without this state catalog, failures become ambiguous and triage slows down.

## 6. Secret storage and access policy

- Store secrets in the approved vault/secret manager only.
- In docs, publish **references** (path/key name), never secret values.
- Restrict read access by role (`qa_lead`, `qa_automation`, `platform_oncall`).
- Record each credential handoff in your change log or ticket system.

Recommended fields per secret reference:

| Field | Example |
|-------|---------|
| Secret path | `kv/raas/qa/partner/basic_api_key` |
| Environment | `qa` |
| Scope/profile | `partner` / `qa-partner-basic` |
| Owner | `platform-security` |
| Created at | `YYYY-MM-DD` |
| Expires at | `YYYY-MM-DD` |
| Rotation ticket | `PLAT-1234` |

## 7. Rotation and rollover playbook

Define a no-downtime rollover process:

1. Create new key/cert.
2. Validate in smoke tests.
3. Announce cutover window.
4. Update QA references.
5. Revoke old credential.
6. Confirm no active test jobs still use old secrets.

Track SLA:

- Emergency rotation SLA (compromised secret).
- Planned rotation cadence (for example, every 90 days).

## 8. Credential request workflow

Every request for new credentials should include:

- Environment.
- Scope/profile requested.
- Tenant.
- Purpose (test suite, exploratory, release validation).
- Required validity window.

Suggested ticket states:

`requested` -> `approved` -> `provisioned` -> `validated` -> `active` -> `rotated/revoked`

## 9. Failure handling and escalation

If authentication tests fail, classify first:

- Invalid credential format.
- Expired/revoked credential.
- Missing required scope.
- Wrong tenant or environment.
- mTLS handshake issue.

Escalate with:

- Timestamp + timezone.
- Environment + base URL.
- Endpoint and response code/body (sanitized).
- Correlation ID (if available).
- Profile ID used (not the secret value).
