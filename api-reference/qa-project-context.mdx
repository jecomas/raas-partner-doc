**Scope:** The **Partner API** as **exposed online** (B2B integrations and widgets). This document does not cover other product APIs.

**Audience:** QA team.  
**Purpose:** First deliverable in a series; **business and contract** framing to design the **test plan** against the published service.

**Assumption:** QA does **not** need access to source code, infrastructure setup, or deployments. **Base URLs**, **test credentials**, and **contract documentation** (OpenAPI, guides, webhooks) are provided by the platform or product team.

**Repository:** Canonical copy in `docs/qa/PROJECT_CONTEXT.md`. Linked from [API Reference](/api-reference/introduction). Keep the Markdown file and this page in sync when editing.

## 1. What you are testing

The **Partner API** lets each **partner** (tenant) run cross-border financial operations: requesting and sending funds, quotes, tokenized payment methods, and identity (KYC) flows, according to **corridors** (routes, limits, fees) and each integration’s rules.

Many flows return an **immediate HTTP response** and complete or report the outcome **later** (async processing and **webhooks**). The test plan should cover both the call response and the final observable state (follow-up queries, webhooks, or criteria agreed with the business).

## 2. How to run tests

- Work against the **base URL** and **environment** (sandbox, pre-production, production) specified by the owning team.
- Use standard API testing tools (Postman, Insomnia, scripts, etc.) and any **collections or examples** officially shared, if available.
- Log findings with enough context to reproduce them (endpoint, method, environment, approximate time, correlation IDs if the API returns them).

Repository clones and local builds are not assumed.

## 3. Domain areas the test plan should reflect

| Area | What to validate (high level) |
|------|-------------------------------|
| **Operations / transactions** | Lifecycle (e.g. pending, sent, failed); amounts and currencies consistent with the agreed corridor. |
| **Quotes** | Validity window; alignment with the operation confirmed afterward. |
| **Payment methods** | Tokens or references per documentation; avoid real card data in shared environments (PCI requirements). |
| **KYC / CIP** | Onboarding and verification flows. |
| **Corridors** | Min/max limits; allowed currencies; restrictions by user level or tenant configuration. |
| **Webhooks and events** | Delivery, retries, and consistency with what the API shows; details in the **webhook specification** provided by the project. |
| **Multi-tenant** | Isolation: one partner’s data and rules must not be accessible to another tenant using a different key; each partner uses its own credentials. |

## 4. Authentication and authorization

- Most operations require an **`api_key`** header (or the mechanism documented for your environment).
- Permissions are grouped into **scopes** (e.g. `partner`, `partner_send`, `partner_full`). The same scenario may pass with one key and fail with another if the scope does not match the endpoint.
- **mTLS** may be enabled for integrations that use a **different base URL** and client certificates. If it applies to your plan, coordinate certificates and environment with the platform team; do not share credentials over insecure channels.

**Exact scope definitions** (values, inheritance, evaluation rules): **[Partner API scopes](/api-reference/partner-api-scopes)**. **Per-endpoint** detail remains in the environment’s OpenAPI and in Mintlify (**Partner API scopes**).

**Best practices:** Do not post **API keys**, tokens, or personal data in tickets, chat, or shared documents inappropriately; rotate credentials after any exposure.

## 6. Documentation and contract

The platform team should provide (or link to) at least:

- **OpenAPI specification** (or equivalent) for the Partner API in the environment you test.
- **Integration guides** (recommended flows, error codes, limits).
- **Webhook contract** (events, payloads, signing or verification if applicable).

A common **request funds** reference flow is: obtain user token → user registration (if needed) → contact → payment method → money request. Exact operation names and order are defined in the current documentation.

## 7. Async behavior and external dependencies

- After a **202 Accepted** response (or another “accepted for processing” signal), the final outcome may arrive via **webhook** or by polling state per the guide.
- Define **maximum wait times** in the plan and what counts as pass/fail (including webhook retries).
- External services (identity, payments, notifications) can add **variable latency** or sandbox downtime: distinguish product defects from provider limitations.

## 8. When something fails (information to escalate)

Collect **anonymized** information when possible:

- Date and time (with time zone), **environment**, and **base URL** used.
- HTTP method, path or operation, **response code**, and error body (no personal data).
- Any **correlation ID** returned by the API (e.g. in headers or body), if documented.

This helps the platform team locate the incident in their operations tooling.

## 11. Short glossary

| Term | Meaning |
|------|---------|
| **RaaS** | Remittance as a Service; in this document, exposed via the Partner API. |
| **Tenant / Partner** | Integrated organization with its own configuration and credentials. |
| **Corridor** | Route and rules between origin and destination (currencies, limits, fees). |
| **KYC / CIP** | Customer identification and fraud / compliance controls. |
| **Webhook** | HTTP notification from the server to a partner endpoint when an event occurs. |
